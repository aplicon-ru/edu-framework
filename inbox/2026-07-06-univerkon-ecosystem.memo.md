## Уточнение понимания: «Учебное событие ≠ Занятие» (§4 academic-concept v1.4)

Из academic-concept §15 (гипотеза «Образовательная активность» и её проверка):

> «Родовое понятие введено в ядро под именем "Учебное событие" (§4), занятие /
> день практики / аттестационное событие — его частные случаи.»

**Иерархия сущностей:**

- **Учебное событие** (D04) — родовое; общее: момент+длительность, состав
  (буфер→факт), свидетель+валидатор, генерация обязательств
  - **Занятие** — пара (2 ак. часа), в сетке расписания; способ = очно/онлайн/гибрид
  - **День (этап) практики** — рабочий день, вне сетки; свидетель = база/СКУД/скан,
    валидатор = кафедра
  - **Аттестационное событие** — 1..N обязательств одновременно (профмодуль СПО
    закрывает несколько МДК); свидетель = комиссия, валидатор = председатель

**Следствие для заходов 2-3 (D04/D14 из Дидактикона):**

6-состоянийный цикл Дидактикона (`запланировано → регистрация → регистрация_закрыта
→ идёт → завершено + перенесено`) — это **цикл занятия как частного случая**, не
универсальный цикл учебного события. У практики и аттестационного события — свои
циклы (у практики — «направление → период дней → защита»; у аттестации —
«назначение → проведение → протокол»).

Значит модель D04 после заходов должна выглядеть так:

```
Учебное событие (родовое)  ─────  общий короткий цикл (запланировано → идёт → завершено)
  ├── Занятие              ─────  расширенный цикл (+регистрация, +перенос) — из Дидактикона
  ├── День практики        ─────  цикл направления → дни → защита (из §17 academic-concept)
  └── Аттестационное событие ───  цикл ведомости → сессия → протокол
```

### Заход 2 — обогащение D04 (следующий PR) — СКОРРЕКТИРОВАНО

**Уточнение после сверки с academic-concept v1.4:** большинство концепций Дидактикона
из Блока III применимо к **Занятию как частному случаю учебного события**, а не к
родовому. Разведение важно, чтобы не сломать инварианты частных случаев (у практики
и аттестации нет «регистрации» в том же смысле, что у аудиторного занятия).

Забрать в D04 из Дидактикон Блок III, аккуратно раскладывая по уровням:

**На уровне «Учебное событие» (родовое) — обогатить общее:**
1. **Двухфазность форм контроля**: открыто → готово → сдано → оценено, бинарное
   принятие (это работает для всех частных случаев)
2. **Пять фактов формы контроля**: assignment → launch → attempt → submission →
   evaluation (общая механика)
3. **Классы форм контроля — три оси**: `role_in_rating (required/bonus)`,
   `assignment_mode (all/per_student)`, `time_model (inline/extended)` — работает
   везде, где есть форма контроля
4. **Терминологическое разведение** «Пересдача формы» (авто, без approval) vs
   «Отработка пропуска» (approval-based) — критично, у нас смешано
5. **Педагогический бонус** как отдельный механизм — вне пакета/ФОС
6. **Assignment group** для вариативных форм
7. **Инвариант «один главный педагог на занятии»** — MVP-принцип

**На уровне «Занятие» (частный случай) — отдельно:**
8. **6-состоянийный жизненный цикл занятия**: запланировано → регистрация →
   регистрация_закрыта → идёт → завершено + перенесено
9. **Регистрация как процесс аутентификации присутствия** — явное состояние с
   `pending/confirmed/rejected` (у нас сейчас неявное через буфер)
10. **Принудительное завершение inline-форм** при переходе занятия в `завершено`
11. **Педагогическая и студенческая проекции карточки занятия** (две проекции
    одной сущности)

**Не забирать (специфика реализации UX):**
- Runtime-пульт с 3 зонами (это UX Дидактикона)
- Polling 60 сек
- Конкретные дедлайны и настройки
- Двухсимвольные `time_model: inline | extended`  → взять на концептуальном уровне
  без обязательства использовать именно эти имена

### Что НЕ забираем в edu-framework

Специфика реализации, остаётся в описании implementations:

- Инверсия устойчивости (write locally first, sync async) — паттерн ИС, не методология
- OIDC + машинные credentials (mTLS, TPM) — специфика реализации
- SCORM/cmi5 адаптер, JS-объект `API`/`API_1484_11`
- IndexedDB / Service Worker / PWA
- Runtime-пульт педагога с 3 зонами — UX-специфика Дидактикона
- Конкретный LRS и его выбор
- CDN/статика для контента
