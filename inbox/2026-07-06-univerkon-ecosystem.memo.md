## Уточнение понимания (после доклада 2026-07-06)

Ранее моё понимание опиралось на academic-concept v1.4 §4: учебное событие —
родовое понятие; занятие/практика/аттестация — частные случаи. Доклад руководству
(`2026-07-06-doklad-digital-infrastructure.pdf`) добавляет ключевой нюанс:
**события планируются на уровне плана, а не создаются расписанием.**

### Иерархия и владение

**D06 — норма-ось.** Именно здесь **формируется план учебных событий**:
- **В РПД / РПП** — план событий **внутри дисциплины** (занятия, модульные контроли,
  промежуточная аттестация)
- **В УП** — план событий **между дисциплинами / уровня программы** (экзамены,
  зачёты, курсовые, ГИА)

Единый план учебных событий существует **в двух уровнях**, оба живут в D06.

**D05 — контингент, траектория.** Персональная развёртка УП+РПД для обучающегося
с учётом его выборов, перезачётов и т.д. Траектория знает: **какие события
предстоят этому обучающемуся**.

**D14 — расписание.** **Не создаёт события — разворачивает их.** Берёт готовый
план из D06 и накладывает на сетку ресурсов (аудитории, преподаватели, потоки),
учитывая выборы обучающихся. Слот расписания = дата, время, аудитория,
преподаватель + ссылки на 1..N запланированных учебных событий.

**D04 — реализация.** Свершившееся учебное событие: буфер→факт, свидетель+
валидатор, обязательства, записи, задолженности.

### Учебное событие как термин

Из доклада (§4):
> «На это имя завязана вся математика модели, структура данных, документация,
> рабочий язык команды. Это несущая стена: изменив название, придётся переписывать
> весь каркас.»

**Термин «учебное событие» остаётся в стандарте фреймворка** (совпадает с
academic-concept v1.4). Занятие / экзамен / зачёт / день практики / модульный
контроль / курсовая / ГИА — всё это учебные события разных видов.

### Разведение «занятие» ↔ «слот расписания»

В обиходе слово «занятие» имеет два значения:

- **«Занятие» как учебное событие** — генератор обязательств «присутствие + текущий
  контроль». Тип: занятие (лекция / семинар / практика / лаба).
- **«Занятие» как слот расписания** — временной интервал + ресурсы. Один слот может
  содержать **1..N учебных событий**: само занятие + модульный контроль темы + текущий
  контрольный тест и т.д.

Пример из фразы автора: «на одном занятии может быть модульный контроль, причём
в нём могут участвовать не все» — здесь «занятие» = слот, а «модульный контроль»
= отдельное учебное событие внутри слота с другим (меньшим) составом.

Модель D14 хранит **слоты**, каждый ссылается на N запланированных событий из
D06. Модель D04 хранит **факты проведения** этих событий с составом и записями.

### Жизненный цикл учебного события (сквозной, через D06/D14/D04)

```
D06:  Запланировано в РПД/УП (тип, дисциплина, привязка к теме)
        │
D05:  Появляется в траектории обучающегося (кому предстоит)
        │
D14:  Развёрнуто в слот расписания (дата, аудитория, преподаватель, ресурсы)
        │
D14:  запланировано → регистрация → регистрация_закрыта → идёт (цикл Дидактикон
                                                                    для типа «занятие»)
        │
D04:  Наступает: состав фиксируется (пересечение траектории × статуса),
      буфер, свидетель+валидатор, обязательства
        │
D04:  Записи → закрытие обязательств → задолженности
```

Пункт «запланировано → регистрация → регистрация_закрыта → идёт → завершено» из
Дидактикон Блок III — это **цикл слота расписания** (D14) для типа «занятие/экзамен/
пересдача/отработка». У дня практики свой цикл; у аттестационного события уровня
программы — свой. Внутри слота порождаются учебные события D04 в момент
наступления.

### Три задолженности — одна механика (из доклада §5)

Все три — вычисляемые состояния над **той же** механикой событий и обязательств:

- **Дисциплинарная** — из событий внутри дисциплины (пропуск занятия, несданный
  модульный контроль, незащищённая лабораторная)
- **Академическая** — из аттестационных событий уровня программы (экзамен,
  курсовая, ГИА). Здесь работает ФЗ-273 ч. 5 ст. 58 (2 попытки, год)
- **Финансовая** — из событий учебного календаря по договору

Значит финансовый контур D09 тоже говорит на языке учебных событий (наступил
семестр → обязательство по договору).

### Заход 2 — обогащение D04/D06/D14 (следующий PR) — ПЕРЕСМОТРЕНО

**Разбить работу по трём доменам** согласно уточнённой иерархии выше:

**D06 (норма-ось) — обогатить:**
- **План учебных событий в РПД / РПП** — перечень запланированных событий
  внутри дисциплины (занятия, модульные контроли, промежуточная аттестация).
  Событие в плане имеет тип, привязку к теме/модулю, форму контроля,
  ожидаемую длительность.
- **План учебных событий уровня программы в УП** — экзамены, зачёты, курсовые,
  ГИА (события между дисциплинами).
- **Единый план** — оба уровня сшиваются в единый план УП+РПД, из которого потом
  разворачивается расписание и вычисляется траектория.
- **Пакет занятия как манифест** (из lesson-package-concept + §7 доклада «картридж») —
  привязан к дисциплине/теме/виду; НЕ знает группу/дату/преподавателя. Один
  пакет — много запусков.
- **Gate как первоклассная сущность** (из lesson-package)

**D14 (расписание) — доработать:**
- **Слот расписания** — единица D14: дата, время, аудитория, преподаватель +
  ссылки на 1..N запланированных учебных событий из D06
- **Жизненный цикл слота (для аудиторного занятия)**: запланировано → регистрация
  → регистрация_закрыта → идёт → завершено + перенесено (6 состояний Дидактикона)
- **Регистрация как процесс аутентификации присутствия** — pending/confirmed/rejected
- **Именованный отбор** — правило состава слота (уже есть в D14)
- **Расписание разворачивает план, не создаёт события** — контракт D14 ← D06

**D04 (реализация) — обогатить:**
- **Учебное событие остаётся родовым** (academic-concept v1.4 §4). Терминология
  зафиксирована как «несущая стена».
- **Двухфазность форм контроля**: открыто → готово → сдано → оценено, бинарное
  принятие
- **Пять фактов формы контроля**: assignment → launch → attempt → submission →
  evaluation
- **Классы форм контроля — три оси**: `role_in_rating (required/bonus)`,
  `assignment_mode (all/per_student)`, `time_model (inline/extended)`
- **Разведение** «Пересдача формы» (авто, без approval) vs «Отработка пропуска»
  (approval-based) — критично, у нас смешано
- **Педагогический бонус** как отдельный механизм — вне пакета/ФОС
- **Assignment group** для вариативных форм
- **Инвариант «один главный педагог на занятии»**
- **Состав события формируется как пересечение** (кто имеет событие в траектории D05)
  × (кто активен на дату). Формулировка §4 доклада: «состав каждого учебного
  события формируется в момент его наступления, из тех, у кого это событие
  стоит в траектории и чей статус позволяет на нём быть».
- **Одно "занятие в расписании" может содержать несколько учебных событий**
  (пример из фразы автора): само занятие + модульный контроль темы. У каждого свой
  состав, свои обязательства.

**D05 (контингент) — уточнить:**
- **Траектория** — вычисляемое представление: развёрнутый УП обучающегося с учётом
  выборов и перезачётов. Знает: какие события предстоят этому обучающемуся.
  У нас в D05 траектория уже описана как «представление, не хранимая сущность» —
  подтверждается.

**D09 (финансы) — сверить:**
- **Финансовая задолженность** — вычисляемое состояние над той же механикой
  событий и обязательств. Наступление события учебного календаря →
  обязательство по договору. У нас в D09 это уже есть по факту (начисление
  привязано к академическому событию); терминологически можно проговорить связь.

**Не забирать (специфика реализации UX):**
- Runtime-пульт с 3 зонами (это UX Дидактикона)
- Polling 60 сек
- Конкретные дедлайны и настройки
- Двухсимвольные `time_model: inline | extended` → взять на концептуальном уровне
  без обязательства использовать именно эти имена

### Заход 3 — новая сущность «Пакет занятия» в D06 (отдельный PR)

Из `lesson-package-concept.md`:

1. **Пакет = манифест** (не контейнер контента, ссылки на материалы)
2. **Стейтлесс** — всё состояние во внешнем LMS
3. **Три источника данных**: base (из ИС) + overlay (педагог) + runtime (LMS)
4. **Провенанс**: id / version / revision / schema_version
5. **Gate как первоклассная сущность** — 6 видов (entry-test, consent, briefing,
   readiness, form, attendance); entry/exit размещение
6. **Тесты в пакете как спецификация выборки из банка**
7. **Активности vs разделы** — дихотомия, оставить как открытый вопрос
8. **Виды занятий** — закрытый справочник в D04/D06

### Что НЕ забираем в edu-framework

Специфика реализации, остаётся в описании implementations:

- Инверсия устойчивости (write locally first, sync async) — паттерн ИС, не методология
- OIDC + машинные credentials (mTLS, TPM) — специфика реализации
- SCORM/cmi5 адаптер, JS-объект `API`/`API_1484_11`
- IndexedDB / Service Worker / PWA
- Runtime-пульт педагога с 3 зонами — UX-специфика Дидактикона
- Конкретный LRS и его выбор
- CDN/статика для контента
