## A. Корпус: что это за документы

Пять файлов делятся на две группы. **Это не данные, а метамодели** — спецификации
структуры нормативных актов и рабочих программ, выраженные в таблице. Каждая ячейка
размечена типом через легенду (см. раздел B).

### Группа 1 — стандарты (вход D06)

| Файл | Что описывает | Структура |
|------|---------------|-----------|
| ФГОС ВО (Б/С/М) | стандарт высшего образования | I. Общие положения · II. Тр. к структуре · III. Тр. к результатам · IV. Тр. к условиям |
| ФГОС аспирантуры/ординатуры | стандарт с ДВУМЯ редакциями в одном шаблоне (`Н` = новый, `14` = стандарт 2014) | те же 4 раздела; II выделен в два листа (`прогр. Н` и `прогр. С-14`) |
| ФГТ аспирантуры | федеральные гос. требования (научные кадры) | 3 раздела; иная несущая ось — **Научный компонент + Образовательный компонент** вместо блочной структуры |

Каноническая структура ФГОС (инвариант между ВО и аспирантурой):

- **Раздел I. Общие положения** — параметры программы: формы обучения; ЭО/ДОТ;
  форма реализации (самостоятельно/сетевая); язык; сроки по формам; объёмы в з.е.
  (min/max); области, сферы, типы задач ПД (ссылки на справочники);
  направленность (профиль). В версии-14 добавлены объекты/виды ПД и проф. задачи.
- **Раздел II. Требования к структуре** — Блок 1 «Дисциплины (модули)»,
  Блок 2 «Практика», Блок 3 «ГИА»; обязательная часть / часть, формируемая
  участниками; формирование компетенций (УК/ОПК/ПК); объёмы блоков в з.е. (min/max).
- **Раздел III. Требования к результатам** — вкладки УК/ОПК/ПК;
  цепочка компетенция → индикатор (см. раздел E).
- **Раздел IV. Требования к условиям** — общесистемные, материально-технические,
  кадровые (доли % с min), финансовые, механизмы оценки качества.

ФГТ — компрессия той же идеи: 1. Научный компонент (научная деятельность → диссертация,
публикации/РИД, промежуточная аттестация по этапам) · 2. Образовательный компонент
(дисциплины, практика, промежуточная аттестация) · 3. Итоговая аттестация;
+ индивидуальный план (научной деятельности / учебный).

## B. Легенда как DSL (наблюдаемая система типов полей)

Весь корпус покрывается шестью примитивами + маркерами применимости:

**Типы полей:**
- `V` — булево
- `0` — число (ввод)
- `min / max` — диапазон (ограничение, а не скаляр!)
- «из справочника …» / «документ Excel "Справочник — …"» — ссылка на классификатор
- «ручной ввод» — свободный текст
- «из учебного плана» / «автоматически из раздела …» — вычисляемое/связанное поле

**Маркеры применимости поля:**
- `Н` / `14` — редакция стандарта (новый / 2014) — ФГОС аспирантуры
- `СПО` / `ВО` / `ДПО` / `СПО-ВО` — уровень образования — шаблоны РП

Вывод: перед нами неформальный язык описания форм. Универкон может формализовать его
в машиночитаемую схему (JSON/YAML) с типами, диапазонами, предикатами применимости
и ссылками на справочные домены.

## C. Заготовки для Универкон (что берём)

1. **Каноническая 4-раздельная схема нормативного акта.** Готовый типизированный
   скелет для `standards/fgos/schema` (+ реестр D01): дерево из четырёх поддеревьев
   с фиксированной семантикой. ФГТ — его 3-раздельная компрессия. D06 схему
   *потребляет* для сборки/валидации ОПОП и УП, но не владеет ею.

2. **Мини-система типов полей (легенда DSL).** Переносима на любой продуктикон с формами.
   Провалидирована на живом корпусе. Кандидат в `common`-слой, а не в D06.

3. **Предикат применимости поля — first-class сущность.** Одна каноническая форма
   + feature-флаги на полях над осями `(уровень образования, редакция стандарта)`.
   Не N параллельных форм. Прямое подтверждение битемпоральности/снимков D06.

4. **Реестр справочных доменов (классификаторы).** См. инвентаризацию в разделе D.
   Каждый — адресуемый, версионируемый, переиспользуемый между D04/D05/D06.

5. **Компетентностная несущая стена.** Непрерывная трассируемость
   стандарт → … → ФОС. Общий шов Дидактикон ↔ Тестикон. См. раздел E.

6. **Учебное событие = «Карточка темы (занятия)».** Атом уже описан:
   схема учебного пакета урока и вход в runtime-пульт Дидактикона. См. раздел F.

7. **Типизированный ресурсный бюджет (часы → з.е.).** «Трудоёмкость» изоморфна
   событийному бюджетированию ПФХД. См. раздел G.

8. **Контракт валидации (min/max как инварианты).** Норма хранит ограничения,
   программа — значение, валидатор проверяет `значение ∈ диапазон`.
   Предмет проверки — учебный план относительно снимка стандарта. Стиль Тестикона.

9. **«Условия реализации» = стык нормы и состояния ОО.** Раздел IV (аудиторный фонд,
   ЭИОС, кадровые доли %, учёные степени, финансы, оценка качества) — точка встречи
   нормативного акта с описанием состояния организации из edu-framework.
   РП тянет помещения «автоматически из раздела Аудиторный фонд».

## E. Компетентностная нить (несущая стена) — детально

Непрерывная цепочка, тянущаяся по всем слоям:

```
Стандарт (III раздел)
  → группа (УК / ОПК / ПК)
    → Компетенция (код + наименование)
      → Индикатор (1.1, 1.2, 1.3 …)
        → Дескриптор / результат обучения (Знать / Уметь / Владеть)   ← слой РП
          → Форма контроля
            → ссылка на базу тестов (ФОС / Тестикон)
```

Замыкание на уровне занятия (РП, «Карточка темы»): поля
**«Формируемые компетенции»** и **«Соотнесение с требованиями к результатам освоения»**.

Нюанс редакции-14: во ФГОС ординатуры III раздел различает структуру вкладок
для нового стандарта (компетенция → индикаторы) и для 2014 (компетенция ↔ вид
профессиональной деятельности). Предикат применимости работает и здесь.

Что нужно, чтобы это стало трассируемостью, а не текстом: **единый стабильный
идентификатор** компетенции/индикатора, на который ссылаются норма, РП, событие и ФОС.

## F. Схема учебного события (из «Карточки темы / вида занятия»)

**Три вида одного понятия, разного масштаба** (решено ранее, подтверждено
разбором таблиц): занятие (одна тема в одной РП, ниже) · день практики ·
событие-аттестация (закрывает предмет, несколько предметов сразу, или целый
блок — тогда это ГИА). Не три разные сущности — один список событий, разного
охвата. Живут на двух уровнях: подробные занятия — внутри конкретной РП;
события-аттестации (в т.ч. закрывающие сразу несколько предметов, вплоть до
ГИА) — на уровне учебного плана, не привязаны к одной РП.

Поля атома для подтипа «занятие» (1 карточка = 1 занятие):

- Дисциплина / модуль *(из учебного плана)*
- Тема занятия *(ручной ввод)*
- Вид занятия *(справочник)*
- Длительность: **Пара = 2 ч / Урок = 1 ч** (+ количество)
- Цель *(ручной ввод)*
- Аннотация
- Методы обучения *(справочник)*
- Средства обучения *(справочник)*
- Форма контроля *(справочник)* — здесь это **текущий контроль** (проверка
  именно на этом занятии, много раз за период; не путать с промежуточной
  аттестацией — см. раздел N)
- Формируемые компетенции *(справочник)*
- Соотнесение с требованиями к результатам освоения

Подтип «событие-аттестация» несёт свою форму (Экзамен/Зачёт/Зачёт с оценкой/
Курсовая работа/Госэкзамен/Защита ВКР) как **собственное** поле — это и есть
промежуточная аттестация; позиция(и) плана (раздел L, п.4) на него лишь
ссылаются, не дублируют форму у себя.

Контекст сверху — «Тематический план»: № семестра/триместра → модуль/дисциплина →
Тема N → Занятие N (тип: лекционное/практическое) с контактной работой в часах
(формат `000/000` — по формам обучения).

## G. Типизированный ресурсный бюджет (таксономия «Трудоёмкости»)

Вёдра часов из РП дисциплины (не сумма — типизированные ресурсы):

Лекционные занятия · Лекции с ЭО/ДОТ · Практические · Лабораторные · Семинарские ·
Консультации · Контроль самост. работы (КСР) · Контактная работа на аттестацию в ТО
(АтТО) · Контактная работа на аттестацию в экз. сессию и ГИА (ЭкГИА) ·
Самостоятельная работа · Контроль (самост. работа в экз. сессию) ·
Контактные часы на практику (КчП) · Оформление отчётности по практике (ОП) ·
Практика · Аттестация → **ИТОГО в часах → ИТОГО в ЗЕ**.

Формы контроля: Экзамен / Зачёт / Зачёт с оценкой / Курсовая работа
(+ комплексные и квалификационный экзамен для СПО).

Изоморфизм с ПФХД: тот же типизированный ресурс + сверка с ограничениями (min/max
из стандарта). Проверить, покрывает ли одна алгебра бюджета и деньги, и часы.

## K. `satisfies` — отношение constraint→instance (решено, вопрос 1 закрыт частично)

Итог спора прокурор/адвокат: constraint↔instance — **не примитив поля**, а
**примитив отношения**, второй ярус `common` (примитивы формы — шесть типов;
примитивы связи — как поля из разных схем сцепляются).

**`satisfies(источник_поле, целевое_поле)` несёт два атрибута:**
- `kind` — вид ограничения. Закрытый enum, **три вида** (не два — расширен после
  разбора ДПО/СПО): `range` (min/max), `subset` (компетенции РП ⊆ компетенций
  стандарта), `threshold-tier` (часовой порог → ступень с разными следствиями,
  напр. тип итогового документа; не binary valid/invalid, а классификатор).
- `strength` — сила связи: `hard` (ФГОС — нельзя нарушить) / `soft` (типовая
  программа ДПО — можно отклониться с обоснованием) / `absent` (нормы нет вовсе).

Источник нормы (ФГОС / типовая программа профильного ведомства / профстандарт
Минтруда) — это **не форк схемы связи**, а обычный атрибут самого нормативного
документа (уже живёт в `standards/`/D01). `satisfies` ссылается на документ,
не дублирует его происхождение.

Валидатор **генерируется** из задекларированных `satisfies` (git-as-truth —
не пишется руками параллельно схеме). Обкатка — сперва на паре `fgos ↔ rpd`
(range, subset); `threshold-tier` и `soft` проверить на живом ДПО-кейсе, когда
дойдём. D04/D05 (HR-конкурсы, приёмка) — отложены до подтверждения на этой паре.

**Конверсионная константа (часов → з.е.)** — сама нормативный параметр, а не
глобальная неизменная величина: версионируется вместе с диапазонами внутри
`fgos/schema`. Атом хранения (типизированный бюджет часов, раздел G) один и тот
же для всех уровней; з.е. — вычисляемая свёртка через эту константу, а не
альтернативная единица хранения. Округление на границе диапазона при конвертации
(вверх/вниз/до ближайшего) должно быть явным правилом валидатора, не умолчанием.

**Отложено к отдельному обсуждению → частично снято.** Иерархия перечня
дисциплин/практик — **не вложенное дерево хранения, а плоский список** атомарных
позиций плана. То, что выглядит «деревом» (Блок 1/2/3, Научный/Образовательный
компонент, ПМ) — это **реквизиты (категориальные атрибуты) на плоской строке**,
используемые для группировки при построении печатной формы (официального
документа плана), а не физические контейнеры. Реквизиты не конкуренты —
сосуществуют на одной строке независимо:
- принадлежность к блоку/компоненту (для печатной группировки);
- покрытие общим терминальным событием (нужно только части строк — ПМ закрывается
  квалификационным экзаменом, Научный компонент ФГТ — диссертацией; для большинства
  строк ВО это поле пусто);
- обязательная часть / часть, формируемая участниками (бюджетно-авторская доля);
- **вид вариативности** — уточнённая ось выбора, три значения: `обязательно-без-выбора`
  / `обязательно-с-выбором` (элективная корзина) / `факультатив` (вне обязательного
  объёма). Структурно похоже на `satisfies.strength` (тоже три значения), но это
  другая ось — не «норма обязывает значение», а «план обязывает студента взять
  единицу»; не путать и не сливать в один enum.

Для `обязательно-с-выбором`: корзина выбора в печатной форме, как правило, —
**одна строка** с одной формой контроля и одним объёмом (план утверждается до того,
как известен конкретный выбор студента; конкретные варианты внутри корзины —
отдельная ссылочная связь один-ко-многим, не дополнительные строки плоского списка
на том же уровне). Внутри корзины два требования разной твёрдости:
- **объём (з.е.) — жёсткий структурный инвариант**, а не конвенция: принадлежит
  самому слоту, варианты его наследуют. Держит валидатор `range` осмысленным —
  сумма плана против диапазона ФГОС проверяется на этапе проектирования, до выбора
  студента (план — снимок, не зависящий от будущей траектории); если бы трудоёмкость
  варианта отличалась, сумма плана стала бы зависима от индивидуального выбора.
  Равенство здесь **построчное** (одна строка = одна строка внутри настоящей
  корзины — «дисциплина vs дисциплина»). *Поправка: профиль/трек — это не ветка
  корзины и не агрегатное равенство внутри плана — профиль это другой план
  целиком (отдельный документ ОПОП/учебного плана). Выбор профиля пинится так же,
  как год набора — до плана, а не внутри его плоского списка. Каждый профильный
  план проверяется против диапазона ФГОС независимо; планы разных профилей не
  обязаны совпадать по сумме друг с другом.*
- **форма контроля — мягкая институциональная конвенция** (ради опрятности печатной
  формы и единого расписания сессии), не питает ни один `satisfies`-check напрямую;
  стоит закодировать как необязательную проверку согласованности, а не инвариант.

**Вопрос 1. Где живёт метамодель — в D06 или в `common`?**
→ *решение: два яруса `common` — примитивы формы (6 типов) + примитивы связи
(`satisfies`, см. раздел K). D06/`fgos` — потребители, не владельцы. Обобщение
на D04/D05 отложено до обкатки на паре fgos↔rpd.*

**Вопрос 2. Как моделировать применимость `Н/14` и `СПО/ВО/ДПО`?**
→ *решение: тритемпоральность отклонена. «Редакция» и «уровень образования» —
одна и та же природа: **категориальный дискриминатор, каким документом является
норма**, а не ось времени — по той же логике, что «год набора — пин, не ось версии»
(решено ранее для D05/`ОПОП_Version`). Каждая редакция (Н, 14) — отдельный
адресуемый документ в `standards/fgos/data` со своей собственной битемпоральностью
(valid-time+transaction-time), если сама редакция впоследствии правится приказом;
битемпоральность остаётся ровно как была, применяется *внутри* каждого документа,
а не между Н и 14 — они не сменяют друг друга во времени, а действуют параллельно
(старые когорты доучиваются по 14, новые идут по Н), поэтому один валидный-момент
не может дать одну активную версию — значит это не временная ось вообще.
Программа пинится на конкретный документ (редакция × уровень), как и раньше.
Легенда `Н/14` из xlsx — схемное удобство для авторинга: на уровне
`standards/fgos/schema` выражается дискриминатором + условной применимостью полей
(JSON Schema if/then или oneOf), а не полем в самих данных.*

**Вопрос 3. Как физически провести компетентностную нить (шов Дидактикон ↔ Тестикон)?**
→ *решение: новый механизм не нужен — переиспользуется `satisfies(subset)` (раздел K)
на грануляции индикатора, а не всего набора компетенций разом.
- **ID — составной, скопирован документом, не вечный глобальный.** `компетенция =
  (document_id, код)`, `индикатор = (document_id, код_компетенции, код_индикатора)`
  (напр. `FGOS-VO-44.03.04-2021#УК-1.1`). Согласовано с решением вопроса 2 — раз
  редакции не версии одной сущности, код не может быть «вечным» через все редакции.
- **Хаб — РП.дескриптор, не норма напрямую.** РП.дескриптор → `satisfies(subset)` →
  норма.индикатор (единственная точка входа в норму). Карточка занятия
  «формируемые компетенции» и ФОС/тест-item ссылаются на РП.дескриптор, а не на
  норму — одна точка входа вместо трёх при перевыпуске нормы.
- **Родословная (ФГОС vs профстандарт) — дискриминатор на ссылке.** Ссылка несёт
  `{тип: фгос|профстандарт, document_id, путь}`; путь — `[компетенция,индикатор]`
  либо `[функция,действие]` в зависимости от типа.
- **Outbox — существующая шина Универкона**, не новый канал. Изменение нормы →
  событие → `D06-P02` слушает → обратный индекс `satisfies`-связей находит
  затронутые РП.дескрипторы → пересборка. Обратный индекс — побочный продукт
  хранения `satisfies` как таблицы.*

**Вопрос 4. Один движок бюджета или два (часы ↔ деньги)?**
→ *решение: общее ядро + два инструмента, не одна алгебра целиком.
Ядро (общее) — типизированный гроссбух: событие → тип ресурса → количество →
сумма → `satisfies(range)` против версионируемого ограничения. Растёт из той же
триады событие→обязательство→запись, что уже лежит в основании учебного события —
не новое изобретение, а тот же корень. Разное — не форма, а вес:
(1) конверсия вверх (часы→з.е. — линейная константа) не имеет денежного аналога;
(2) справочник статей — разный классификатор (раздел D), не разная алгебра;
(3) регуляторный вес — казначейский контроль/аудит/раздельный учёт источников
у денег есть, у часов физически нет; сращивание в один буквальный модуль раздуло
бы часовой движок лишним аудитом или ослабило бы денежный. Один буквальный код —
преждевременная конвергенция (тот же риск, что в вопросе 1 с D04/D05).*

**Вопрос 5. Иерархия перечня дисциплин/практик — единая или по backbone-профилю?**
→ *решение: плоский список + набор некомпетирующих реквизитов (блок/компонент,
покрытие терминальным событием, обязательная/вариативная доля, вид вариативности
3-значный). «Дерево» — артефакт печатной формы (group-by при рендере), не хранения.
Корзина `обязательно-с-выбором`: объём (з.е.) — жёсткий построчный инвариант
(обслуживает `range`-валидатор). Профиль/трек — НЕ ветка корзины, а отдельный
план целиком, пинуется как год набора; планы разных профилей не обязаны совпадать
по сумме. Форма контроля — мягкая конвенция, не инвариант. Закрыт.*

## J. Предлагаемый следующий шаг (обновлено после закрытия всех 5 вопросов)

Все развилки I закрыты. Порядок обкатки — от простого и проверяемого к сложному:

1. **`satisfies` на паре fgos↔rpd** (вопрос 1/K): реализовать три вида ограничения
   (`range`, `subset`, `threshold-tier`) + атрибут `strength` (hard/soft/absent)
   только на этой паре. D04/D05 — не трогать, пока пара не доказана.
2. **Составные ключи компетенций** (вопрос 3): `(document_id, код)` для
   компетенции/индикатора; РП.дескриптор как единственный хаб-потребитель нормы;
   событие и ФОС ссылаются на дескриптор, не на норму напрямую.
3. **Документ на редакцию, не поле-флаг** (вопрос 2): `Н` и `14` — отдельные
   файлы в `standards/fgos/data`, каждый со своей битемпоральностью; легенда
   `Н/14`/`СПО-ВО-ДПО` из xlsx превращается в дискриминатор+conditional на уровне
   `standards/fgos/schema`, не в поле данных.
4. **Плоская таблица плана** (вопрос 5): один список позиций + реквизиты
   (покрытие событием, обязательная/вариативная доля, вид вариативности);
   раздел/блок для печати — не хранится, вычисляется из других пометок
   (см. раздел L); печатная форма — group-by при рендере, не хранении.
5. **Общее ядро гроссбуха** (вопрос 4): типизированный гроссбух ресурса как
   абстракция, часовой и денежный (ПФХД) инструменты — отдельные реализации сверху.

Эталон для шага 1–3 — ФГОС ВО + РП дисциплины; проверить на аспирантуре (`Н/14`)
и ФГТ до генерации форм ввода и валидатора учебных планов.

## L. Таблица «Перечень дисциплин/практик» — согласованная структура

Плоский список позиций плана. Одна позиция = один предмет или одна практика.
У каждой позиции:

1. Название.
2. Обязательная часть стандарта / часть, добавленная вузом.
3. Вид выбора: без выбора / с выбором из нескольких (тогда рядом список
   вариантов) / факультатив (не входит в обязательный объём).
4. Ссылка на событие-аттестацию, которое закрывает эту позицию (промежуточная
   аттестация: экзамен/зачёт/защита и т. д. — это свойство САМОГО события,
   раздел F, не отдельная пометка здесь; событие может закрывать сразу
   несколько позиций разом, вплоть до целого блока — тогда это ГИА).
5. Часы по видам (лекции/практика/лаб/самостоятельная и т. д.) + сумма
   в часах и в зачётных единицах.
6. Ссылка на **конкретную версию** рабочей программы (не «на программу вообще» —
   план должен помнить именно ту версию, под которую он собирался, чтобы не
   «поплыть» вслед за более поздними правками программы).
7. Когда это происходит (семестр/курс) — отдельная таблица «график», разберём далее.
8. Только для практик: место прохождения.
9. Ответственное подразделение.

**Раздел для красивой печати (Блок 1/2/3) — НЕ хранится отдельно.** Вычисляется
на лету из уже имеющихся пометок: если заполнено «место практики» — это
практика (Блок 2); если событие-аттестация в п.4 имеет форму госэкзамен/защита
и охватывает целый блок — это итоговая аттестация (Блок 3); иначе — обычный
предмет (Блок 1). Отдельная пометка правильно оказалась лишней.

**Компетенции сюда не входят вовсе** — они целиком живут в рабочей программе
(через ссылку из пункта 6), не дублируются в этой таблице.

## M. Таблица компетенций — согласованная структура

Два разных списка, не один — важно не смешивать.

**Каталог требований стандарта.** Не хранится отдельно в D06 — приезжает вместе
с документом стандарта (`standards/fgos/data`): группа (УК/ОПК/ПК) → компетенция
(код+название) → индикатор (мелкий пронумерованный пункт). Просто часть самого
документа нормы.

**Рабочие связи РП (это и есть «дескрипторы» из раздела E).** Одна строчка =
«эта рабочая программа обещает конкретное знание/умение/навык ради конкретного
пункта стандарта». В строчке:
- текст — что именно должен уметь студент (пишет автор программы);
- указатель на пункт стандарта — составной адрес: `(document_id, код_компетенции,
  код_индикатора)`, см. решение вопроса 3;
- для ДПО, завязанного на профстандарт — тот же указатель, но путь
  `[трудовая_функция, трудовое_действие]` вместо `[компетенция, индикатор]`
  (дискриминатор типа, см. вопрос 3);
- (опционально) сила связи — жёсткая (гос. стандарт обязателен) или мягкая
  (типовая программа/рекомендация), см. раздел K.

**Единственная дверь в норму.** Занятие («формируемые компетенции») и вопрос
теста ссылаются на эту строчку РП, а не на стандарт напрямую — консистентно
с хабом из решения вопроса 3.

**Матрица компетенций — не отдельное хранилище, а вычисляемый вид** (сводная
таблица «предмет × компетенция»), собранный из тех же строчек-указателей —
тот же принцип, что и раздел для печати в разделе L: удобное представление,
не то, что лежит в основе.

## N. Таблица «График (периоды)» — согласованная структура

Не календарь с датами — таблица позиций на шкале времени, своя у каждого
учебного плана (не общая: «семестр 5» осмыслен только внутри конкретной
программы — у бакалавриата/специалитета/магистратуры разный срок обучения).

Одна строка = один период при нужной грануляции. Пометки: курс, семестр/триместр
(в зависимости от того, как устроена программа), неделя, день. Плюс тип периода
(для крупноблочной сетки всей программы): учебные недели / сессия / практика /
итоговая аттестация / каникулы.

**Многосеместровый предмет не имеет собственного отдельного списка разбивки** —
вместо этого пара «предмет + период» с трудоёмкостью (часы по видам из
раздела G), привязанной именно к этой паре, а не к предмету целиком или к
периоду целиком. Итоговая трудоёмкость предмета (раздел L, п.5) — сумма по всем
таким парам этого предмета.

**Учебное событие (раздел F, «Карточка темы») ссылается на период** (скорее
всего неделю) — не ради точной даты, а чтобы можно было отсортировать события
одной рабочей программы в правильном хронологическом порядке. Настоящая дата
(аудитория, день недели) появляется позже, в отдельном домене-оркестраторе
расписания — сюда не входит.

**Уточнение терминов (снята коллизия названий).** «Форма контроля» использовалась
для двух разных вещей на разных уровнях — стоило развести раньше:
- **промежуточная аттестация** — не пометка на паре «предмет+период», а
  **само событие-аттестация** (раздел F, третий подтип учебного события):
  ссылается на период, как и обычное занятие, и несёт форму (Экзамен/Зачёт/…)
  как собственное поле. Позиция плана (раздел L, п.4) лишь ссылается на это
  событие. Если у многосеместрового предмета в разных семестрах разная форма
  проверки — это просто два разных события-аттестации, по одному на семестр,
  каждое ссылается на свой период; вопрос снят, отдельного механизма не нужно.
- **текущий контроль** — проверка на отдельном занятии (раздел F, «Карточка
  темы»), много раз за период, своя на каждом занятии. Другой подтип события,
  другое назначение — не путать с промежуточной аттестацией.

## O. Реализационная заметка: документы 1С по уровням образования

Схема одна (вся статья), но физически в 1С — **разные документы УП на разные
уровни образования (СПО/ВО/ДПО), не один документ с RLS.**

**Почему не RLS.** В 1С права на объект (документ целиком, через роли) почти
бесплатны. RLS платит на каждое обращение — список, отчёт, поиск — и цена
сильно растёт, если условие смотрит не на само поле документа, а в связанную
таблицу (тут: «какое подразделение отвечает за этот уровень» — почти наверняка
требует соединения, не плоское равенство). Систематическая нагрузка на каждый
список планов, а не разовая переплата.

**Разное отвечающее подразделение — сигнал, что и жизненный цикл разный**, не
только права: согласование, подписанты, обязательные реквизиты печатной формы
по уровню — в 1С это и так завязано на документ как единицу (данные+процесс
проведения/согласования вместе). Разделение хранения тут просто честно
отражает то, что и так разное.

**Дисциплина, чтобы не разъехалось.** Разные документы ≠ разный код: валидация
по `satisfies`, генерация печатной формы, структура табличных частей — в общих
модулях, переиспользуются между документами уровней, не копипастятся (тот же
риск расхождения, от которого оберегались с fgos/rpd-словарями).

**Свод «все планы вуза разом», если понадобится** — не повод сращивать
документы обратно. Отдельный регистр сведений/отчётная модель поверх
нескольких типов документов — тот же ход, что в вопросе 4 (общий гроссбух,
раздельные инструменты). Источник раздельный, свод — отдельный слой сверху.
