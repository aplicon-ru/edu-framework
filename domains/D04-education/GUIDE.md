# D04 · Руководство по работе с доменом

## Как определить, что изменение относится к D04

D04 — **что происходит** в учебном процессе. D05 — **с кем** (физлицо в статусе обучающегося).

| Ситуация | Домен |
|---|---|
| Преподаватель проводит занятие и фиксирует присутствие | D04 |
| Студент получает оценку на экзамене | D04 |
| Студент уходит в академический отпуск | D05 (приказ) + D04 (таймер задолженности останавливается) |
| Студент отчисляется за неуспеваемость | D05 (приказ) — D04 поставляет основание |
| Кафедра выставляет ведомость | D04 |
| Ректорат издаёт приказ о выговоре | D05 (факт) — D04 поставляет триггер |
| Студент записан в журнал практики | D04 |
| Студент меняет группу | D05 |
| Оценка попала в зачётку | D04 (запись) через D04 (ведомость); обложка зачётки — D05 |

## Центральная абстракция: Учебное событие

Всё начинается с события — датированного факта учебного процесса. Событие порождает для
каждого участника пучок **обязательств** (что должно быть сдано/зачтено). Обязательства
закрываются **записями**. Задолженность — это обязательство уровня дисциплины, для которого
нет положительной записи после даты сессии.

```
Событие → Обязательства (1 на участника × форму контроля)
              ↓
         Записи (первичная / отработка / пересдача / сторно)
              ↓
         Задолженность = вычисляется (не хранится)
```

Три частных случая:
- **Занятие** — пара в сетке расписания; способ (очно/онлайн/гибрид) — атрибут, не класс.
- **День практики** — вне сетки; свидетель от базы, **валидирует кафедра** (критичное
  разделение: нельзя допустить подлог через самовалидацию).
- **Аттестационное событие** — закрывает 1..N дисциплин; для профмодуля СПО — несколько МДК
  одним событием.

## Состав события: черновое → факт через буфер

Состав события — это **факт присутствия**, не проекция группы. Это значит:
- До истечения технологического буфера (например, 3 дня) состав можно корректировать.
- После буфера состав затвердел: изменение — только сторно документом.
- Перевод студента в другую группу **не меняет** прошлое присутствие.

Размер буфера — параметр учётной политики.

## Типовые ошибки

**Прямая правка записи вместо сторно.**
Нарушает неизменяемость факта. Аудитор не сможет восстановить историю. Всегда: сторно
исходной записи + новая запись с правильным значением.

**БРС как ядро модели.**
БРС — это одна из политик оценивания, не ядро. Политику можно поменять (другой весовой
алгоритм, «зачёт/незачёт» без рейтинга), не трогая механику событий и обязательств.

**Задолженность как объект, а не вычисляемое состояние.**
Задолженность не хранится — она вычисляется: есть ли обязательство уровня дисциплины без
положительной записи после даты сессии. Не создавайте отдельную таблицу «долгов».

**Автоматическое отчисление по истечении срока задолженности.**
[Просрочена] требует доказанной неявки на реально предложенный слот. Срок истёк, но слот не
предлагался → задолженность НЕ переходит в [Просрочена]. Отчисление — документ, не автомат.

**Компетенции добавлены в событие.**
Измерение сформированности компетенций опирается на агрегат форм контроля — это отдельный
**слой планирования**. Не смешивайте с контуром реализации: событие знает о форме контроля,
не о компетенции из стандарта.

**Журнал использован как источник КЦП-финансирования.**
Для бюджетников источник оказанного объёма — контингент (D05) + ведомости, не журнал.
Журнал → D09 только для расчёта возврата платных студентов.

## Таймер задолженности

```
Срок = (Дата возникновения + 1 год) − Периоды-исключения
```

Периоды-исключения (академотпуск, болезнь, БиР) — факты D05, D04 берёт **снимок** на дату
возникновения задолженности. При новом периоде-исключении таймер пересчитывается.

Потолок — 1 год (ч. 5 ст. 58 ФЗ-273, ⚠ сверить). Организация может установить короче.

## Что делать при ошибке в составе события после буфера

1. Создать сторно документом-основанием (приказ или служебная записка с датой).
2. Сторно ссылается ровно на одну запись.
3. Создать новую запись с правильным значением.
4. Основание хранится — нужно для аудита.

## Периодичность контрольных действий

| Действие | Когда |
|---|---|
| Проверка не закрытых обязательств модуля | Перед закрытием модуля (кафедра) |
| Формирование ведомостей сессии | По учебному календарю |
| Подготовка графика пересдач | До начала ликвидации задолженностей |
| Контроль истекающих таймеров задолженности | Ежемесячно (УМУ) |
| Передача данных оказанного объёма в D09 | По запросу / при отчислении |
