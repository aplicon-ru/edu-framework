### Решено — технический долг: миграция `sourcePath` в JSON Pointer + живой пример `relationLink`

Оба пункта были в «Открытые вопросы» (пп. 5–6) с прошлого раунда правок РПД-Двойника.

**Миграция `sourcePath`.** Перед миграцией пересчитано заново: не 91, а **76**
значений `sourcePath` в `discipline-program-twin.full-template.json` были в
dot-notation (91 — цифра из другого места, «91 реквизит» шаблона в целом,
по ошибке скопирована в описание этого долга; исправлено). Не мигрировано
слепой заменой точек на слэши — сперва выгружены и проверены все 61 уникальных
значения на предмет коллизий, которых опасался прошлый CHANGELOG. Коллизия
нашлась ровно там, где ожидалась: 6 значений используют собственную нотацию
`[]` для «на каждый элемент массива» (`classroomFund.rooms[].address`,
`content.thematicPlan.periods[].modules[].topics[]`) — JSON Pointer (RFC 6901)
такого понятия не знает вообще: адресует одну конкретную позицию, не «любой
элемент». Наивная замена точек на слэши с отбрасыванием `[]` превратила бы
`rooms[].address` в `/rooms/address` — синтаксически валидный указатель, но
означающий уже «у rooms есть поле address», а не «у каждой комнаты в rooms
есть поле address» — тихая потеря смысла.

**Решение — не изобретать свою нотацию, взять готовую из JSON Schema.**
`sourcePath` адресует не «сырой» экземпляр данных, а канонический источник
(`sourceType`: `curriculum`/`classroomFund`/... — сам по себе категория, не
документ), который по всему нашему стеку описывается через JSON Schema; в
JSON Schema форма «что лежит в каждом элементе массива» — это ключевое слово
`items`. Поэтому `X[].Y` → `/X/items/Y`, `X[].Y[].Z` → `/X/items/Y/items/Z`:
валидный JSON Pointer (никакого расширения спецификации), с точным
сохранением исходного смысла «на элемент массива», не выдуманный с нуля, а
переиспользующий понятие, которое уже везде вокруг есть. Итог — 76 замен,
после — `jsonschema.FormatChecker()` даёт 0 ошибок на всём файле (было решено
и подтверждено проверкой, не просто «должно быть похоже на pointer»).

**Живой пример `relationLink`.** `relations.links` был пуст с момента
появления самого поля — механизм существовал только как контракт схемы, ни
разу не использован на реальных данных. Добавлена первая связь: собственное
поле Двойника `totalCredits` (итоговая трудоёмкость дисциплины в з.е.) →
`standards/fgos/data/FGOS-VO-44.03.04-2017.json#/program/volume_credits`
(реальный файл, реальное поле, значение 240 — проверено чтением файла, не
предположено). `relationType: dependsOn`, не `derivedFrom` — трудоёмкость
одной дисциплины не копирует общий объём программы, а ограничена им
(компонент суммы, не её копия); `comment` явно поясняет разницу, чтобы не
завести привычку путать «производное значение» и «значение, зависимое от
ограничения» под одним типом связи.

### Изменено — вариативность строки плана: электив/факультатив/профмодуль СПО (§1.4, §1.6, §1.11, §1.12)

Продолжение разбора `inbox/2026-07-06-univercon-fgos-rp-konspekt.md` — раздел про
«вид вариативности» (3 значения вместо 2 у `chast`). Разобрано через призму учебного
события (итоговая аттестация по строке плана) и проверено на реальных сценариях: корзина
выбора (иностранный язык, элективы физической культуры), факультатив, профессиональный
модуль СПО (несколько МДК → один квалификационный экзамен), Блок 3 аспирантуры.

**Найден и устранён конфликт с прежним инвариантом «1 РПД : 1 строка плана» (§1.6).**
Строка-корзина (например, «Иностранный язык» с выбором английский/немецкий/французский)
требует нескольких по-настоящему независимых РПД (разное содержание, разный
преподаватель), а не одной. Решение: строка остаётся одна (иначе трудоёмкость варианта
задваивается в сумме против ФГОС), РПД получает собственный явный `disciplina_id`;
1..N РПД на строку, N > 1 только при новом `vid_variativnosti = электив`.

**Новые поля строки плана (§1.4):** `vid_variativnosti` (фиксированная / электив /
факультатив — ось согласия обучающегося, ортогональна `chast`) и `uchityvaetsya_v_obyome`
(bool — исключает факультативы и элективы физической культуры из суммы, сверяемой с
объёмом ФГОС, Инвариант 4). Оба — хранимые, не вычисляемые: план обязывает раньше, чем
дописаны РПД-варианты (тот же временной порядок, что у `trudoyomkost_ze`).

**`promezhutochnaya_forma_id` перенесён со строки (§1.4) на РПД (§1.6).** На строке поле
не могло представить несколько разных форм контроля у нескольких РПД одновременно.
Перенос на РПД одним и тем же механизмом объясняет оба разобранных сценария:
- **электив** — у N РПД одной строки по умолчанию N разных форм → N независимых событий;
- **профмодуль СПО** — у РПД разных строк (МДК + практики) намеренно **одна и та же**
  форма → одно общее событие, закрывающее все обязательства разом. Отдельная сущность
  «Профессиональный модуль» не заводится — совпадения ссылки достаточно.

**Исправлена реальная внутренняя нестыковка в §1.11.** `istochnik` формы контроля
относил уровень «дисциплина» (промежуточная аттестация) к РПД — то есть буквально
утверждал, что тип контроля (экзамен/зачёт) решает кафедра. Это противоречило уже
написанному в §1.6 («РПД не владеет формами контроля — она их проецирует») и реальному
порядку согласования (тип задаёт план/УМО при утверждении, не автор РПД). Дисциплина
перенесена в корзину `УП`; заодно переименовано `uroven: модуль` → `тематический_модуль`
(снята коллизия с профессиональным модулем СПО, у которого нет собственного уровня формы
контроля).

**§1.5:** добавлено пятое значение `tip` — `научные_исследования` (Блок 3 аспирантуры:
строка плана без тематического плана занятий, РПД проецируется без раздела «Тематический
план»).

**Новые инварианты 16–19** (§3): электив — 1..N РПД, не N строк; профмодуль — расшаренный
`promezhutochnaya_forma_id`, не контейнер; `vid_variativnosti` — хранимое, не вычисляемое;
блоки печатной формы плана (Б1.О/Б1.В/ФТД/…) — вычисляемый вид группировкой по
`tip`×`chast`×`uchityvaetsya_v_obyome`, кроме профмодуля.

⚠ **Регуляторика, требующая сверки:** норма «не менее 328 академических часов, не
переводятся в з.е.» для элективов физической культуры и спорта — общее знание о ФГОС
3++, не проверено построчно по тексту конкретного стандарта. Приказ Минобрнауки № 266 от
24.03.2025 (заменил № 499 с 01.09.2025) как основание для ДПО — факт замены подтверждён

(упомянутая в §1.6 «Вариант ДПО») — не подтверждена первоисточником. Статус аспирантуры

активном движении, `uroven` в §1.6 пока не тронут намеренно.

### Решено — «Вопрос 2» конспекта (common-ярус) закрыт без новой архитектуры

По итогам разбора `inbox/2026-07-06-univercon-fgos-rp-konspekt.md`, раздел K
(«Где живёт метамодель — в D06 или в `common`?»): **новый слой строить не
нужно**. Проверка на фактах показала, что предложенные примитивы уже
реализованы в `standards/rpd/schema/discipline-program-twin.schema.json`,
влитом в предыдущем PR, просто под другими именами:

| Предложение конспекта | Уже есть в РПД-схеме |
|---|---|
| 6 типов полей (DSL) | `fieldSource` (`sourceType`/`fillMode`/`sourcePath`) |
| `satisfies(kind, strength)` | `validationRule` (`type: range/crossField/...`, `severity: info/warning/error/critical`) |
| Связь между документами (fgos↔rpd) | `relationLink` (`from/to/relationType`), явно описан как «связи Двойника с ФГОС» |

`relationLink.links` в эталонном шаблоне пока пуст — механизм существует, но
ни разу не заполнен реальной связью. Отдельно рассмотрен вопрос про SHACL
(W3C-стандарт именно под задачу `satisfies`) — не принят: SHACL работает над
RDF-графами, весь наш стек — чистый JSON Schema; адаптация означала бы
непропорциональный сдвиг ради одной пары документов. Наш `validationRule` —
по сути SHACL, упрощённый до чистого JSON под реальный масштаб задачи.

**Принято одно точечное улучшение — адресация как JSON Pointer (RFC 6901).**
Проверены реальные форматы: `fieldSource.sourcePath` и `relationLink.from/to`
были объявлены как свободная строка без формата. Добавлены `format:
json-pointer` (для `sourcePath`) и `format: uri-reference` (для `from`/`to`,
поддержка ссылок на внешние файлы вида `standards/fgos/data/FGOS-VO-...json#/...`)
— используем существующий IETF-стандарт вместо изобретения своей нотации.
JSON-LD (W3C, более тяжёлый вариант с внешней совместимостью) рассмотрен и
отложен — нет текущей потребности во внешних потребителях наших данных как
связанных (linked data); пересмотреть, если фреймворк когда-нибудь станет
источником открытых данных для внешних систем.

⚠ **Технический долг, зафиксирован явно (решено — см. запись выше в
«[Не выпущено]»):** 76 значений `sourcePath` (не 91 — эта цифра по ошибке

### Архитектурное решение (зафиксировано в проектной сессии)

- **Норма-ось целиком в D06**, не в D04. Основание: D06 = «УМД и контент» по названию;
  ФЗ-273 ст. 2 определяет ОПОП как единый комплекс документов — разрывать его между доменами
  неестественно. D04 остаётся контуром реализации (что произошло), D06 — норма (чему и как).
- РПД = норма-слой (D06); учебно-методический контент, рождающийся из РПД, = контент-слой
  (тоже D06, отдельный слой, наполняется позже).
